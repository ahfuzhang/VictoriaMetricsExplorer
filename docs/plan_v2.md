# 用户个性化收藏与菜单存储实施计划 v2

- 更新日期：2026-10-22
- 初稿：[plan_storage.md](./plan_storage.md)
- 适用项目：VictoriaMetrics Explorer Grafana App Plugin
- 状态：设计与实施计划；本文没有把待验证的接口能力视为已经实现。

## 1. 目标与关键决策

实现 **Grafana 服务器端的用户个性化存储**：每个用户可以管理自己的目录树，在收藏节点中保存多个完整查询；这些数据持久化到 Grafana 服务器使用的数据库，在其他浏览器登录同一 Grafana 实例后从服务器重新读取。

保留初稿的核心要求：React 前端调用 Grafana User Storage API；菜单与节点内容分开保存；用 Protobuf 定义业务数据；采用 `Protobuf → gzip → Base64` 编码；支持目录、收藏节点及其拖动管理。前端负责界面、编码和发送请求，Grafana 服务端负责认证、授权与数据库持久化。用户存储不经过本 App 的 Go 后端；执行收藏中的查询仍复用现有 Go 查询接口。

### 1.1 存储位置与职责

```text
React 页面内存中的编辑状态
  → Protobuf → gzip → Base64
  → HTTP 请求：Grafana User Storage API
  → Grafana 服务端 → Grafana 使用的持久化数据库

再次打开 App
  → 从 Grafana User Storage API 读取服务器数据
  → Base64 解码 → gzip 解压 → Protobuf 解码
  → 在 React 页面中显示
```

**Grafana 服务端数据是唯一持久化来源。** 菜单、文件夹、收藏节点、PromQL、名称、单位、数据源绑定、自增 ID、版本和操作回执全部随对应业务消息存储在服务器端。部署必须为 Grafana 数据库配置持久化，Grafana 进程或容器重启后仍可读取。

浏览器仅保留当前页面生命周期内的内存状态，用于展示、编辑和减少重复解码；这不构成保存。该功能不得把数据写入 localStorage、sessionStorage、IndexedDB、Cache Storage 或其他浏览器持久化介质，也不得在服务器不可用时回退到这些介质。编辑草稿未提交前只在内存中，刷新或关闭页面可能丢失，界面必须明确其未保存状态。

“保存成功”仅指 Grafana 服务端已确认提交；客户端编码完成、更新 React 状态、写入内存缓存都不能触发成功提示。清空浏览器数据、切换设备不影响已经保存的收藏。

### 1.2 关键决策

以下是本计划相对初稿补充或明确的决策：

| 事项 | v2 决策 | 原因 |
| --- | --- | --- |
| 持久化位置 | 仅存储到 Grafana 服务器使用的数据库 | 用户数据应随 Grafana 用户身份恢复，不依赖原浏览器 |
| 收藏对象 | 保存查询文本、可读名称、单位、数据源及必要显示配置 | 只有指标名不足以还原用户的查询 |
| 树节点 | 文件夹与收藏节点使用显式类型；只有文件夹可包含子节点 | 避免把查询集合误当成目录 |
| ID | 保留树内自增 ID，但在服务端条件提交成功时才算分配完成 | 多标签页不能分别读旧值后无条件写回 |
| 写入边界 | 同一个 User Storage 资源内，一次条件请求提交菜单和所有相关内容 Key | 两次 `setItem()` 不能构成事务 |
| 前端 SDK | 不直接把 `usePluginUserStorage().setItem()` 用作可靠持久化协议 | 已安装 SDK 存在静默本地回退、缓存和缺少条件写入的问题 |
| 接入方案 | 封装前端 REST adapter，调用 Grafana 服务端 User Storage API；先验证资源版本冲突语义 | 前端直接发起请求，数据由 Grafana 服务端持久化 |
| 多查询展示 | 首版在第二栏列出节点内查询，第四栏显示所选查询；不自动执行整个节点 | 支持多查询保存，同时控制请求量和四栏改造范围 |
| 运行上下文 | 查询绑定保存时的数据源；时间范围与 Step 使用当前工具栏 | 避免换数据源后执行到错误环境，避免保存过期时间窗口 |
| 旧收藏 | 可选的一次性导入来源；用户选择后读取旧列表并提交到服务器，不再写入或维护旧列表 | 兼容已有历史数据，不延续浏览器存储方案 |
| 不支持环境 | 原有指标浏览可继续使用，个性化保存明确失败或不可用 | 不提供任何浏览器持久化回退 |

上述展示与上下文规则是初稿未明确部分的首版建议，实施时以本文为默认行为。目录管理、多个查询、单位配置和再次打开收藏均属于首版闭环。

## 3. 范围与产品行为

### 3.1 首版必须完成

1. 登录用户从 Grafana 服务器加载菜单，向服务器保存修改，并在清空浏览器数据或更换设备后恢复。
2. 文件夹与收藏节点的创建、重命名、排序和跨层级移动。
3. 删除收藏节点；仅允许删除没有任何子节点的文件夹。
4. 从第四栏 Favorite 打开保存界面，创建节点或向已有节点追加查询。
5. 一个节点保存多个查询；每条查询可编辑名称、表达式和单位，可排序、删除。
6. 从菜单打开节点、选择查询并执行，显示实际数据或独立错误状态。
7. 持久化失败、并发冲突、损坏数据、接口不可用均有可恢复路径。
8. 提供用户主动选择的旧收藏一次性导入，导入结果只保存到 Grafana 服务器。

### 3.2 本次不包含

团队共享、权限分享、生成 Grafana Dashboard、自动后台同步离线队列、查询模板变量编辑器、跨 Grafana 实例同步、完整版本历史、任意文件导入，以及一键并行渲染整个收藏节点。

不保存查询结果、数据源凭据、API Token 或浏览器身份信息。Protobuf 与 gzip 用于结构化和压缩，Base64 用于字符串传输；这条链路不提供加密。

### 3.3 目录与节点规则

- 菜单根是不可删除的虚拟容器，不占自增 ID；其 `children` 可以包含文件夹和收藏节点。
- 文件夹可以包含文件夹或收藏节点；自身没有查询内容 Key。
- 收藏节点没有 `children`，其内容可包含 0～20 条查询。管理界面允许创建空节点，空节点显示引导；从 Favorite 保存的新节点必须至少有一条查询。
- 文件夹只要存在任意子节点就不允许删除，包括空文件夹、空收藏节点；不提供递归删除。
- 同一父节点下的名称经去首尾空白及 Unicode NFC 规范化后不得完全相同，大小写不同视为不同名称；不同父节点允许重名。
- 文件夹不能移动到自身或任意后代；收藏节点不能成为放置目标。跨父级移动后重新验证同名与深度限制。
- 子节点数组顺序就是显示顺序，不同时维护第二份 `order` 或父指针。
- 重命名、移动和排序不改变 ID；删除后不回收 ID。当前选中节点属于 UI 状态，不作为 ID 分配计数器。

### 3.4 保存界面

保存界面采用可滚动的 Drawer 或 Modal，分为“位置”和“查询”两部分，布局窄时改为上下排列。

**位置部分：** 展示相同的目录树，支持新建文件夹、新建收藏节点、选择已有收藏节点。选择文件夹只表示创建位置，不能直接把查询写入文件夹。已有节点默认执行“追加查询”；“替换已有查询”必须显式选择目标查询。

**查询部分：** 显示可增删、排序的查询列表。每条查询至少包含名称、多行表达式、单位和数据源；高级区域显示图形类型与当前上下文说明。进入界面时使用当前 `ChartPlan` 的最终表达式预填，包含已经生成的 Pod、Node、标签过滤和 rate/increase/irate 计算。

保存界面内新增的目录、节点和编辑的查询先放入页面内存草稿；点击保存后整体提交到 Grafana 服务器。取消关闭不产生服务器目录，也不写入浏览器存储。存在未保存修改时，关闭界面需由用户选择丢弃或继续编辑。

加载新 ChartPlan 期间、没有当前请求对应的查询时禁用 Favorite。查询已生成但数据执行失败时仍允许保存定义，错误不会被解释为保存失败。打开保存界面后固定快照，不因后台刷新或工具栏变化覆盖用户草稿。

### 3.5 打开收藏与四栏布局

| 栏位 | 普通浏览模式 | 收藏浏览模式 |
| --- | --- | --- |
| 第一栏 | Pod、Node、Metric、旧收藏入口 | 同一导航树，最下方显示用户菜单 |
| 第二栏 | 指标列表 | 当前节点的查询列表，按保存顺序显示 |
| 第三栏 | 标签过滤 | 所选查询的表达式、名称、单位、数据源；提供编辑入口 |
| 第四栏 | 自动生成的图表 | 执行所选查询并显示图表 |

进入节点默认选择第一条查询；空节点不发请求。切换查询、时间范围、Step 或点击 Refresh 时重新执行当前查询。收藏模式不调用指标 Facets，也不把第三栏旧的标签过滤附加到已保存表达式上。

每条查询绑定 `datasource_uid`。收藏模式的数据源控件展示所选查询的数据源；更换绑定在编辑界面显式完成，不能因普通浏览模式切换了数据源而静默改变。节点内允许不同查询使用不同数据源。

数据源删除或无权限时仍可查看、编辑、移动和删除收藏，并提示选择新的有权限数据源。收藏加载与管理应独立于数据源能力探测失败。退出收藏模式恢复普通浏览的选择状态，避免 `datasourceUID` effect 将收藏选择意外清空。

## 4. Grafana User Storage 的能力与接入方案

### 4.1 已确认的事实

官方文档说明 User Storage 将用户数据保存到 Grafana 数据库，在 Grafana 12.0 起 GA，11.5 起可通过 `userStorageAPI` feature flag 使用。文档也说明 SDK 在服务未开启时可能回退到 localStorage；**本计划不采用这一回退行为**。其服务端数据面向当前用户，且不是加密存储。[官方说明](https://grafana.com/developers/plugin-tools/how-to-guides/add-user-storage)

本工作区 `@grafana/runtime@12.4.13` 的实现显示：

- 公开 Hook 提供 `getItem` / `setItem`，没有公开删除、批量提交、刷新缓存或条件写入接口。
- 多个业务 Key 实际位于同一个资源的 `spec.data: Record<string, string>` 中。
- 已登录请求也可能在请求失败后写入 localStorage，并让 `setItem` 正常结束。
- SDK 缓存和内存锁不构成跨浏览器同步或服务端并发控制。

依据是本地 `node_modules/@grafana/runtime/dist/esm/utils/userStorage.mjs` 及对应的[上游版本源码](https://github.com/grafana/grafana/blob/v12.4.13/packages/grafana-runtime/src/utils/userStorage.tsx)。因此，不能用“`await setItem()` 返回”或再次调用缓存中的 `getItem()` 判断远端持久化成功。

### 4.2 推荐实现：隔离的前端 REST adapter

通过 Grafana `getBackendSrv()` 使用当前用户会话访问 User Storage API。组件只访问应用自己的 Repository，不散落拼装 URL，不导入 runtime 私有的 `UserStorage` 类。URL 由受支持版本的 adapter 根据 `config.namespace` 和当前用户标识构造，并验证 Grafana 子路径部署。

参考实现的资源形式为：

```text
/apis/userstorage.grafana.app/v0alpha1/namespaces/{namespace}/user-storage/{pluginId}:{userUid}
```

这是需要锁定版本与集成测试的适配细节，并非承诺此路径在所有 Grafana 版本中永远稳定。页面内存缓存键必须包含实例、namespace/组织、用户和插件 ID；切换用户或组织时废弃旧会话的内存缓存、草稿和在途响应。每次新页面会话都从服务器初始化，不能从浏览器持久化数据初始化收藏。

下面两组接口只用于组织前端调用服务器的代码：`UserStorageSnapshot` 表示“一次从服务器读回来的数据及其版本”，`UserStorageAdapter` 表示“读取、首次创建、修改服务器数据的方法”。它们不负责浏览器持久化，也不是新增的服务器接口。

```ts
// 一次读取 Grafana User Storage 资源得到的快照。
// 页面可以暂存在内存中；真正持久化的数据仍在 Grafana 数据库中。
interface UserStorageSnapshot {
  // Grafana 返回的整个资源版本，修改时原样带回服务器。
  // 若另一个浏览器已修改资源，服务器应拒绝旧版本提交，避免覆盖其修改。
  // 这是不透明字符串，不自行加 1，也不转换为 JS number。
  resourceVersion: string;

  // 服务器资源的 Key → 字符串值映射。
  // 本功能的 Key 如 favorites.menu.v1、favorites.node.v1.2；
  // 对应值是 Protobuf → gzip → Base64 后的字符串。
  // 资源还可能包含其他功能的 Key，修改时必须保留。
  data: Record<string, string>;
}

// 前端访问 Grafana User Storage API 的统一入口。
// 方法内部发 HTTP 请求；不使用 localStorage 等浏览器存储。
// 条件提交的具体 HTTP 协议须先通过第 4.3 节的真实服务端验证。
interface UserStorageAdapter {
  // 重新请求服务器，读取当前资源，不能直接返回旧的页面缓存。
  // 仅在 API 可用且该用户资源尚未创建时返回 null；请求失败应报错。
  loadFresh(): Promise<UserStorageSnapshot | null>;

  // 用户第一次保存、且服务器资源不存在时，创建整个资源。
  // 若资源已被其他客户端创建，应报冲突，不能覆盖；返回服务器确认的快照。
  create(data: Record<string, string>): Promise<UserStorageSnapshot>;

  // 在已有资源上一次性提交菜单、节点内容等相关 Key 的变更。
  // 成功返回新快照；版本冲突、无权限、网络失败等由调用者分别处理。
  commit(
    // 本次修改依据的资源版本，取自最近一次 loadFresh() 的结果。
    expectedResourceVersion: string,

    // 只列出要改变的 Key：字符串表示新增/替换，null 表示删除该 Key。
    // 未列出的 Key 保持不变；菜单和对应内容必须在同一次请求中提交。
    changes: Record<string, string | null>
  ): Promise<UserStorageSnapshot>;
}
```

注意两个 `null` 的含义不同：`loadFresh()` 返回 `null` 表示整个用户资源尚未创建；`changes` 中某个 Key 的值为 `null` 表示删除这个 Key。采用何种 HTTP PATCH 表达由 adapter 负责。不得通过 DELETE 整个 User Storage 资源来删除一个收藏节点。所有读写错误向上返回分类结果；adapter 不提供任何浏览器存储实现或回退实现。

### 4.3 第一阶段必须验证的契约

Grafana 的该资源使用 Kubernetes generic registry，具有对象 metadata 和 `spec.data`。这为“单资源条件更新”提供了实现依据，但**本次仅阅读了源码，没有对运行实例执行写入验证**。[资源类型](https://github.com/grafana/grafana/blob/v12.4.13/pkg/apis/userstorage/v0alpha1/types.go)、[存储注册](https://github.com/grafana/grafana/blob/v12.4.13/pkg/registry/apis/userstorage/storage.go)

在隔离测试用户和固定 Grafana 版本上验证：

1. GET 返回 `metadata.resourceVersion`；成功修改后获得新的版本值。
2. 首次 POST 创建；并发 POST 同名资源时有明确冲突结果，不能覆盖。
3. 一次 PATCH 修改两个内容 Key 与菜单 Key，服务端作为一个资源变更提交。
4. 优先测试携带 `metadata.resourceVersion` 的 merge patch；旧版本提交必须被拒绝。若需 JSON Patch 的 `test` 条件或带版本 PUT，单独验证后由 adapter 选择一种确定协议。
5. 条件失败时没有任何 Key 部分更新；删除 map 成员语义明确。
6. 保留所有不属于本功能的 Key；拒绝越权访问其他普通用户的资源。
7. 验证 Viewer、Editor、Admin、匿名、用户/组织切换、Grafana 子路径和 API 关闭场景。
8. 确认实际请求体与资源体大小限制、错误码、代理限制、读取一致性。
9. 保存后清空浏览器站点数据并重新登录，验证内容仍从服务器恢复；在另一个独立浏览器读取相同内容。
10. 重启使用持久化数据库的 Grafana 测试实例，验证菜单、节点、自增 ID 和版本仍然存在。

Kubernetes API 中 `resourceVersion` 可用于避免丢失更新，但不能据此跳过 Grafana 目标版本的实测。[API 并发语义](https://kubernetes.io/docs/reference/using-api/api-concepts/#updates-to-existing-resources)

若目标环境无法提供上述条件提交能力，不得用“先读再写”、浏览器锁、时间戳或重试包装伪装成等价实现。应在第一阶段调整存储设计或兼容范围；在条件明确前，个性化写入保持不可用，原有查询功能继续工作。无需为此新增 Go 持久化接口。

### 4.4 版本兼容策略

- 保留已有插件最低版本声明，普通浏览功能继续按原范围运行；个性化存储依能力开启。
- 首先固定一个 Grafana 12.x 验证基线；对实际使用的更新宿主再增加验证记录。安装的 SDK 版本只作为源码参考。
- Grafana 11.6 的开启/关闭 feature flag 两种情况都纳入兼容测试。若通过验证，记录为支持；否则显示该功能不可用，不宣称已兼容。
- 不静态依赖较新宿主独有的 Hook 导出，避免整个 App 在旧宿主加载失败。
- 资源不存在的 404 与 API 路由不存在的 404 需要通过能力探测区分；读取失败不得转换成空树并自动覆盖。

## 5. 数据模型与 Key 设计

### 5.1 业务 Key

保留两类 Key，命名独立于 HTTP API 版本和文档版本：

```text
favorites.menu.v1
favorites.node.v1.<nodeId>
```

`v1` 表示首个存储格式主版本，本计划名称 v2 不意味着存储格式从 v2 起步。目录只存在于菜单；收藏节点 ID 对应一个内容 Key；单条查询不是一个独立存储 Key。

这些 Key 是 Grafana 服务器端同一 User Storage 资源中的 map 成员，不是浏览器存储 Key，也不代表独立数据库行。Base64 字符串值由 User Storage API 写入 Grafana 数据库。拆分 Key 能减少变更和解码范围，但当前 API 的 GET 可能仍返回整个 map；容量与性能评估必须按整个服务端资源计算。

### 5.2 建议的 Protobuf 定义

新增 `proto/explorer/user_storage.proto`，生成到 `src/generated/explorer/user_storage_pb.ts`；仅生成 TypeScript。下面定义的是“保存到 Grafana 服务器的数据长什么样”。前端将这些结构编码后写入 User Storage，读取时再还原成同样的结构。

结构之间的关系是：**Tree 保存整个菜单；TreeNode 保存菜单上的一个文件夹或收藏入口；收藏入口通过 ID 找到 SavedNodeContent；SavedNodeContent 内包含多条 SavedQuery。** `MutationReceipt` 是额外的保存操作记录，用来解决“服务器已经保存，但浏览器没有收到响应”时的重复提交问题。

| 结构 | 回答的问题 | 保存位置 |
| --- | --- | --- |
| `Tree` | 用户有哪些目录和收藏入口？下一个节点 ID 是多少？ | `favorites.menu.v1` 的值 |
| `TreeNode` | 这个入口叫什么、是目录还是收藏、下面有哪些入口？ | 嵌在 `Tree.children` 或其他文件夹的 `children` 中 |
| `SavedNodeContent` | 点击这个收藏入口后，可以选择哪些查询？ | `favorites.node.v1.<nodeId>` 的值 |
| `SavedQuery` | 这条查询执行什么表达式、用哪个数据源、怎样显示？ | 嵌在 `SavedNodeContent.queries` 中 |
| `MutationReceipt` | 某次保存请求是否已经成功，创建了哪些节点？ | 嵌在 `Tree.recent_mutations` 中，与业务修改一起提交 |

Protobuf 的 `message` 字段声明中，`= 1`、`= 2` 等是**字段编号**，不是字段默认值；`enum` 中等号右边则是枚举值。`repeated` 表示列表。`schema_version` 的实际初始值 1 需要创建消息时设置。

```protobuf
syntax = "proto3";
package explorer.userstorage.v1;

// 区分菜单项是“目录”还是“存放查询的收藏入口”。
enum NodeKind {
  NODE_KIND_UNSPECIFIED = 0; // 未设置，不能作为合法节点保存。
  NODE_KIND_FOLDER = 1;      // 文件夹：只有子菜单，没有查询内容 Key。
  NODE_KIND_NODE = 2;    // 收藏入口：没有子菜单，通过 ID 关联查询内容 Key。
}

// 再次打开已保存查询时，使用哪一种图形显示查询结果。
enum VisualizationKind {
  VISUALIZATION_KIND_UNSPECIFIED = 0; // 未设置；保存前需明确图形类型。
  VISUALIZATION_KIND_TIMESERIES = 1;  // 时间序列折线图。
  VISUALIZATION_KIND_STAT = 2;        // 数值展示，首版取各序列最后一个非空值。
  VISUALIZATION_KIND_HEATMAP = 3;     // 热图，查询结果需要符合桶标签结构。
}

// 整个用户菜单，编码后保存到服务器的 favorites.menu.v1。
// 负责导航结构、节点 ID 分配和提交记录，不直接存储 PromQL。
message Tree {
  // 数据格式版本：用于判断当前程序能否读取、修改此格式；初始填 1。
  uint32 schema_version = 1;

  // 整棵树的 UUID。正常编辑保持不变，重建整棵树时才更换。
  // 防止旧页面把上一次树中的节点数据写到重建后的树中。
  string tree_uid = 2;

  // 历史上已分配的最大节点 ID，文件夹与收藏入口共用这个计数器。
  // 空树为 0，下一节点使用当前值 + 1；删除节点后也不减小。
  uint64 max_tree_node_id = 3;

  // 根目录下的菜单项，列表顺序就是显示顺序；文件夹内部继续递归。
  repeated TreeNode children = 5;
}

// 菜单上的一个条目：文件夹或收藏入口。
// 此结构嵌在菜单树中，不单独创建服务器 Key。
message TreeNode {
  // 树内唯一的自增 ID；移动、重命名后不变，删除后不复用。
  // 若为收藏入口，例如 ID=2，其内容 Key 为 favorites.node.v1.2。
  uint64 id = 1;

  // 第一栏菜单显示的名称，例如“服务监控”或“接口延迟”。
  string name = 2;

  // 决定此条目能否包含子菜单，以及是否应关联查询内容。
  NodeKind kind = 3;

  // 只有文件夹可以有子菜单；收藏入口必须为空。
  repeated TreeNode children = 4;

  // 文件夹填 0；收藏入口记录其 SavedNodeContent.revision。
  // 打开收藏时核对两者，避免显示与菜单版本不匹配的旧内容。
  uint64 content_revision = 5;
}

// 一个收藏入口对应的查询集合。
// 编码后保存到 favorites.node.v1.<node_id>，可以包含多条 PromQL。
message SavedNodeContent {
  // 查询集合的数据格式版本，初始填 1；用途与 Tree.schema_version 相同。
  uint32 schema_version = 1;

  // 所属菜单树的 UUID，必须与 Tree.tree_uid 相同。
  string tree_uid = 2;

  // 对应收藏入口的 TreeNode.id，必须与所在 Key 的 ID 一致。
  uint64 node_id = 3;

  // 这一查询集合的业务版本，修改其中内容时递增。
  // 同次提交还要更新菜单中该入口的 content_revision。
  uint64 revision = 4;

  // 该收藏入口内的全部查询；列表顺序就是第二栏的显示顺序。
  repeated SavedQuery queries = 5;

  // 最近修改时间，Unix 毫秒，用于展示；不能用它代替版本冲突检查。
  int64 updated_at_ms = 6;
}

// 一条可以重新执行的查询定义，嵌在 SavedNodeContent.queries 中。
// 保存表达式和显示配置，不保存本次执行得到的时间序列数据。
message SavedQuery {
  // 查询自身的 UUID，用来精确定位要修改、删除或排序的查询。
  // 与树节点的自增 ID 不同；同一次保存重试时继续使用同一 UUID。
  string id = 1;

  // 用户可读名称，例如“接口 P99 延迟”，显示在查询列表和图表标题中。
  string name = 2;

  // 最终执行的完整 PromQL/MetricsQL 文本，包含已确定的过滤条件。
  // 例如 histogram_quantile(0.99, sum(rate(...[5m])) by (le))。
  string expression = 3;

  // 执行查询时使用的 Grafana 数据源 UID，避免换页面后查到其他环境。
  string datasource_uid = 4;

  // 保存时的数据源名称，仅作为显示提示，尤其用于数据源已删除的情况。
  // 不能按此名称寻找数据源；真正寻址必须使用 datasource_uid。
  string datasource_name_hint = 5;

  // 普通折线图或数值图的 Grafana 单位 ID，例如 bytes、s、percentunit。
  // 只影响数字格式化，不改变表达式或原始值。
  string unit_id = 6;

  // 此查询使用折线图、数值图还是热图，重新打开时按此设置显示。
  VisualizationKind visualization = 7;

  // 可选的来源指标名，帮助用户了解查询最初从哪个指标生成。
  // 用户手工新建时可为空；回放始终执行 expression，不从此字段重建。
  string source_metric = 8;

  // 仅热图使用：桶边界的单位，例如延迟桶的 s。
  // 非热图留空；它与桶中的计数或速率单位不同。
  string heatmap_bucket_unit_id = 9;

  // 仅热图使用：桶内数值（颜色所代表数值）的单位，例如次数或次数/秒。
  // 保存 Grafana 单位 ID；非热图留空。
  string heatmap_value_unit_id = 10;
}

```

例如，用户创建“服务监控”文件夹（ID=1），其中有“接口延迟”收藏入口（ID=2），入口内保存 P95、P99 两条查询：

```text
服务器 Key：favorites.menu.v1
  Tree
    max_tree_node_id = 2
    children
      TreeNode(id=1, name="服务监控", kind=FOLDER)
        children
          TreeNode(id=2, name="接口延迟", kind=NODE)

服务器 Key：favorites.node.v1.2
  SavedNodeContent(node_id=2)
    queries
      SavedQuery(name="P95 延迟", expression="...", unit_id="s")
      SavedQuery(name="P99 延迟", expression="...", unit_id="s")
```

上图为省略版本等字段后的逻辑示意，实际服务器值仍是编码后的字符串。点击“接口延迟”时，通过 ID=2 读取并解码对应内容，第二栏列出 P95、P99；选中其中一条后，使用其数据源和表达式执行并显示图表。

### 5.3 数据约束与版本规则

- `schema_version` 初始为 1；`tree_uid` 是首次创建菜单时生成的 UUID，用来识别树被重建等情况。
- `max_tree_node_id` 表示曾分配的最大 ID；新增文件夹和收藏节点都递增。同一次操作创建多个节点时连续分配；删除不降低计数。
- Protobuf `uint64` 在生成的 TypeScript 中按 `bigint` 使用；DOM、map key 和日志中的 ID 转为十进制字符串，禁止转换为 `number` 后再参与计算。
- 树中的 ID 必须非零且全局唯一，并且不超过 `max_tree_node_id`；计数达到 uint64 上限时拒绝新增，不允许回绕。所有内容的 `tree_uid`、`node_id`、revision 必须与菜单引用相符。
- 文件夹的 `children` 可非空，`content_revision` 为 0；收藏节点 `children` 必须为空。未知 kind 进入只读错误状态，不猜测其含义。
- 菜单不重复存储查询名称、表达式或数量；节点名称只在树中维护，防止重命名需要同步多份标题。
- 每次成功业务提交增加 `Tree.revision`；内容变更同时增加对应 content revision。它们服务于应用冲突解释，不能取代服务端 `resourceVersion`。
- UUID 使用浏览器可靠随机源生成；`updated_at_ms` 只用于展示，不作为锁或冲突顺序依据。
- 不改变已发布字段编号，不复用删除字段编号；新增兼容字段保留 unknown fields，避免“PB → 简化对象 → PB”写回时丢失未来字段。
- 遇到高于当前可写版本的数据只读并提示升级，禁止旧客户端重新编码覆盖。

## 6. 编码、容量与校验

### 6.1 编解码流程

业务值使用统一 codec，树与内容均采用同一处理链：

```text
领域校验 → Protobuf 二进制 → gzip → 标准 Base64 → HTTP API → Grafana 数据库
Grafana 数据库 → HTTP API → Base64 严格解码 → 有上限的 gzip 解压 → Protobuf 解码 → 领域校验
```

格式版本由 Key 与消息内版本共同管理，不在 Base64 前额外拼接非 Base64 前缀。首选浏览器原生 Compression Streams，检查 `CompressionStream` 与 `DecompressionStream` 是否存在；支持范围内确有缺口时只增加一个经过验证的 gzip 实现。Web Worker 由实际性能测试决定，首版不预设必须引入。

分块处理字节数组与 Base64，避免对大数组调用展开形式的 `String.fromCharCode(...bytes)`。限制解压输出累计字节，并测试损坏 gzip 与超大膨胀数据；仅在解压完成后检查长度不足以控制内存峰值。

已有 Resource API 的 zstd 编解码保持独立，不复用其编码头或解压器。

### 6.2 首版建议限制

以下是应用建议值，不是宣称 Grafana 官方存在相同配额。第一阶段用真实部署限制校准，后续统一放在 `limits.ts` 中。

| 对象 | 建议限制 | 处理方式 |
| --- | --- | --- |
| 树中全部节点 | 500 个，文件夹和收藏节点合计 | 超出时拒绝新增，仍允许查看、删除 |
| 层级 | 虚拟根深度 0，最深实际节点深度 8 | 创建与移动时检查整个子树深度 |
| 文件夹/节点/查询名称 | 1～128 个 Unicode 码点 | 不截断后写入，明确提示 |
| 每节点查询数 | 最多 20 条 | 保存前验证 |
| 单条表达式 | 最多 16 KiB UTF-8 | 与现有后端限制一致 |
| 解压后的菜单 | 最多 256 KiB | 超出进入只读诊断，不自动清空 |
| 解压后的单节点内容 | 最多 512 KiB | 编码前、解码时均检查 |
| 单个 Base64 值 | 最多 768 KiB | 解码前检查，避免大输入分配 |
| 整个资源候选 JSON | 最多 1 MiB，含已有其他 Key | 计入 Base64、Key、metadata 等开销 |
| 单次加载解压总量 | 最多 8 MiB | 内容按需解码，页面内存缓存采用有界 LRU |
| 幂等操作回执 | 最近 128 条 | 过期后按“不确定提交”流程处理 |

Base64 长度约为压缩字节数的 `4 × ceil(n / 3)`；压缩效果差的数据仍可能超限。节点数和查询数是独立上限，不承诺所有上限能同时达到。超过容量时不得丢弃查询、自动截断树或绕过服务端限制。

上游源码中的“目标小于 3 MB”注释和大小指标不是经过验证的强制配额，不能将其写成平台保证。[大小统计实现](https://github.com/grafana/grafana/blob/v12.4.13/pkg/registry/apis/userstorage/strategy.go)

## 7. 一致性、并发与保存流程

### 7.1 一次业务操作，一次资源提交

Repository 接收领域操作，例如 `createFolder`、`saveQueries`、`renameNode`、`moveNode`、`deleteNode`；组件不得自行按顺序调用多个 Key 的保存方法。

新建节点并保存查询时，同一条件请求包含：更新后的菜单、自增计数器、新节点内容和操作回执。编辑节点内容时同时更新内容 revision 与菜单中的引用版本。删除节点时同时移除菜单引用和内容 Key。这样的原子性以第 4.3 节验证通过为前提。

### 7.2 标准提交步骤

1. 打开编辑界面时记录基础树、目标节点版本和当前身份作用域；创建独立草稿。
2. 用户点击保存后做字段、结构和大小校验，生成一次 `operation_id`，防止重复点击并保留草稿。
3. 从服务器 `loadFresh()` 获取最新资源，不使用 SDK 缓存充当新鲜读。
4. 对比草稿基础版本与最新数据，检查目标是否存在、名称是否冲突、父节点是否改变等。
5. 在最新树上应用领域操作；为草稿中的临时节点 ID 分配正式自增 ID；编码所有变更值。
6. 对完整候选资源检查配额，把菜单和内容变化连同回执放入一次携带资源版本前提的请求。
7. Grafana 服务端确认提交后，使用响应中的新版本更新页面内存缓存与界面；此时才显示“已保存到 Grafana 服务器”。
8. 失败时在当前页面内存中保留草稿并显示具体问题；不写入浏览器存储，不显示保存成功，刷新或关闭页面前提醒草稿尚未提交。

同一页面使用串行写入队列，但它只是减少自身冲突，服务端条件更新仍然必需。第一次建立资源时的并发创建冲突，应重新读取资源后重做同样的校验与分配。

### 7.3 冲突解决规则

| 情况 | 自动处理边界 |
| --- | --- |
| 不同节点被修改 | 重新读取后，在目标前提仍成立时可重新应用操作 |
| 多客户端同时创建节点 | 基于最新 `max_tree_node_id` 重新分配；不能沿用未提交的临时分配值 |
| 同一节点查询集合被另一客户端修改 | 首版提示冲突，保留页面内存草稿，提供查看服务器版本和另存为服务器上的新节点；不自动覆盖 |
| 目录改名或移动 | 目标、原父级、名字和目的地约束仍成立时才重试；否则提示结构已变化 |
| 删除非空文件夹 | 按最新树检查；任何子节点出现都拒绝删除 |
| 待删除收藏节点的内容已被修改 | 展示远端更新提示，由用户重新确认删除，不能自动删除刚被他人客户端更新的内容 |
| 删除已被其他客户端删除的节点 | 重新读取确认后视为已删除，不重建节点 |
| 编辑目标已删除、树 UID 改变 | 停止自动重试；保留草稿，允许重新选择位置另存 |

对可安全重放的冲突最多自动重试 2 次并加入短退避；仍冲突时交给用户处理。不要把某个旧快照作为整体覆盖请求重试。

### 7.4 响应丢失与幂等

HTTP 超时或连接断开不代表提交一定失败。此时先重新加载远端，查找 `operation_id` 回执；找到即说明操作已提交，并利用其中的 ID 映射恢复选择状态。没有回执且仍处于可判定窗口内，才允许用同一个操作 ID 重新尝试。

回执只保留最近 128 条，不能承诺无限期幂等。每次请求保留其基础 tree revision；只有同一树 UID、远端 revision 单调递增且差值小于 128，并确认所有已支持写入路径都保留回执时，才能根据“回执不存在”判定尚未提交。若长时间离线、回执可能已被淘汰或状态无法判定，显示“提交结果待确认”，保留草稿并要求刷新核对；不能自动重复追加查询。查询 UUID 在重试过程中保持稳定，也可辅助判断重复追加。

创建、修改、删除以及迁移、修复都使用同样的服务端回执协议。对于原请求可能仍在服务端执行的情况，重试继续携带版本前提，使两个请求最多一个提交成功。不建立浏览器持久化离线队列或草稿备份；重试所需的临时信息只存在于当前页面内存。关闭或刷新页面后以服务器重新读取的状态为准，不承诺恢复未提交草稿。

### 7.5 页面内存缓存与服务器变更

首次加载从服务器取得资源，只解码菜单，打开节点时再解码相应内容；页面内存缓存以身份作用域、树 UID、节点 ID、内容 revision 为键，页面关闭即失效，不写入任何浏览器存储。应用回到前台、打开编辑界面和保存前重新读取服务器。支持显式刷新；不要求接入服务端 watch。

同源标签页可用 BroadcastChannel 通知失效，但它不能替代服务器校验，也不能保证跨设备实时更新。带草稿的界面收到远端变化时提示版本变化，不覆盖输入。会话切换、节点切换后的旧异步响应都必须通过 generation/request key 检查丢弃。

## 8. 查询回放与显示语义

### 8.1 表达式与时间

- 保存的是最终可执行文本，回放直接调用已有 `query-range`，不再次调用 `chart-plan` 重建表达式。
- 保存时生成的具体 `rate(...[5m])` 窗口等属于表达式内容；修改工具栏 Step 不会自动改写它。
- 首版不支持 Grafana Dashboard 模板变量插值；对 `$__interval`、`$__rate_interval`、`$variable` 给出需要替换为实际表达式的提示，不能悄悄传给上游或通过 `eval` 展开。
- 时间范围始终使用当前工具栏。相对范围在真正执行前重新计算，手动 Refresh 必须推进 `now`，不能沿用旧的绝对起止时间。
- `auto` Step 先转换为明确 duration 再传给后端：根据当前时间跨度与最多约 1000 点的目标选择合适步长，遵守数据源可用的最小采样间隔；未知时给出明确默认值。当前后端把不合法 Step 回退到 1m，因此不能直接用字符串 `auto` 假定获得自动计算。
- 提交前在前端验证查询定义的结构；“试运行”是显式动作。查询无数据、数据源临时无权限或上游不通不应阻止向 Grafana 服务器保存有效定义；语法错误由试运行反馈并保留文本。User Storage 的登录、写入权限和服务器提交仍是保存成功的必要条件。

### 8.2 单位

存储 Grafana unit ID，使用 Grafana 单位选择器或明确映射；UI 可显示中文/英文名称，但不把显示文案作为持久化协议。

| 含义 | 建议 unit ID | 说明 |
| --- | --- | --- |
| 无单位 | `none` | 原始数值 |
| 字节 | `bytes` | 与十进制 `decbytes` 区分 |
| 秒 / 毫秒 | `s` / `ms` | 由表达式原始值的单位决定 |
| 百分比 0～100 | `percent` | 例如 25 显示为 25% |
| 比率 0～1 | `percentunit` | 例如 0.25 显示为 25% |

单位只决定格式化，不隐式乘除原始数据。原 `ChartPlan.unit` 的 `bytes/s`、`s/min`、`%` 等必须经适配转换，不能直接假定都是 Grafana unit ID。速度单位映射和自定义后缀应复用现有显示语义并在支持的宿主上验证。

保存热图时，桶边界的单位与桶计数/速率的单位是两个维度：分别保存 `heatmap_bucket_unit_id` 与 `heatmap_value_unit_id`。不能用“延迟单位”去格式化计数，也不能仅凭来源指标名决定单位。

### 8.3 图形与多序列

- 默认沿用保存时的 `visualization`，手写新查询默认 timeseries。
- timeseries 显示该查询返回的全部受限序列及可辨识图例；禁止复用现有 `.slice(0, 1)` 路径而静默丢数据。
- 首版可设显示上限 100 条序列并明确提示；后端 1000 条上限和响应字节限制仍生效。前端显示上限不能声称降低了已发生的上游查询成本。
- stat 使用清晰的归约规则，首版为每条序列的 last non-null；多序列逐项显示，不擅自求和。
- heatmap 要求符合现有桶标签结构；不满足时提示形状不兼容并允许切换 timeseries。来源图形是提示，不能保证编辑后的表达式仍是直方图。
- 现有 histogram/stat 附加表格由 `chart-plan` 生成，收藏回放首版不伪造或复用旧表格；只展示当前查询结果支持的图形。完整复原分析表格属于后续明确扩展。
- 任何 min/max/avg/sum 都只针对本次返回样本，按序列计算并说明含义；sum 不是时间积分或计数器增量。

### 8.4 请求与错误

为收藏新增返回 `{ frames, meta, step }` 的查询封装，保留原 `queryChartData()` 兼容包装，或同步修改现有调用者。必须显示 `meta.truncated`、有效时间范围及实际 Step，不能只取 frames 丢弃诊断信息。

默认只执行当前选中查询；试运行与正式查询共用调度器，最多 2 个在途请求。切换查询时优先取消旧请求；若当前封装暂不支持网络取消，至少丢弃旧响应并禁止它覆盖新图。单位或名称的纯展示变化无需重新查询。

401/403、数据源失效、PromQL 错误、无数据、被截断和网络超时分别展示。保存成功与执行成功是两种独立状态，不互相覆盖。

## 9. 菜单管理与可访问性

Settings 打开目录管理界面，使用同一套树模型和校验函数。支持新建文件夹/空收藏节点、重命名、删除、拖动排序与修改层级；操作先进入草稿，点击“应用”才提交，取消恢复原树。

拖动具备明确的 before/inside/after 放置反馈；inside 只对文件夹有效。按稳定 ID 而非数组下标追踪拖动项，拒绝拖入自身、后代、超过深度或名称冲突的位置。提交时基于最新树再次验证，拖动时验证通过并不能保证保存时仍合法。

提供“移动到…”、上移和下移等键盘可用的替代操作。树使用 `tree/treeitem/group` 语义，支持展开、折叠、方向键和 Enter；设置按钮有可读名称；Modal 具有焦点约束和关闭后焦点恢复。删除收藏节点明确展示其查询数量并确认；文件夹非空时直接解释不能删除。

第一栏折叠不阻塞从服务器初始化；展开后显示最新状态。新收藏功能的展开、折叠和选中节点等临时 UI 状态只存在于页面内存；如以后要求跨会话恢复这些偏好，也必须扩展服务端模型保存。本次不新增浏览器偏好存储。已有列宽的 localStorage 实现属于现有布局功能，不用于保存任何收藏数据，也不作为本方案的持久化机制。

## 10. 异常、损坏与旧数据迁移

### 10.1 状态与恢复

| 状态 | 用户看到的行为 | 禁止行为 |
| --- | --- | --- |
| 首次使用、API 可用且资源/菜单不存在 | 展示空菜单与创建入口 | 页面加载时主动创建空远端资源 |
| API 不可用或匿名 | 服务器端收藏保存不可用，说明登录或版本条件 | 使用任何浏览器存储保存或回退，无论是否按身份隔离 |
| 读取失败 | 显示重试，允许保留已加载快照只读 | 视为空菜单后写回 |
| 保存失败 | 保留草稿，显示重试或修正方法 | 提前关闭界面、显示 Saved |
| 保存响应不确定 | 显示核对状态，使用操作回执确认 | 直接追加第二份查询 |
| 菜单损坏或版本过新 | 整个收藏区域只读，允许导出原始值诊断 | 自动重置菜单或降低 ID 计数 |
| 某个节点内容损坏/缺失 | 只标记该节点错误；其他节点可读 | 把空内容覆盖原值 |
| 树指向内容但 ID/revision 不符 | 标记不一致，重新读取并停止该节点写入 | 随意选择一份作为正确版本 |
| 存在未被树引用的旧内容 Key | 报告诊断，保留原始数据 | 每次启动自动垃圾回收 |

损坏内容节点允许用户显式删除，删除前可导出原始值；菜单整体损坏时提供备份说明和单独的确认重置流程。重置必须先取得可导出的原始资源，使用新的 tree UID，并在条件提交中处理本功能 Key；不得删除其他插件偏好。

日志仅记录操作类型、大小、耗时、错误类别和版本状态，不打印完整 PromQL、标签值或 Base64 内容。普通用户隔离由 Grafana API 执行，不用前端隐藏菜单代替授权；“仅自己可见”不承诺防止 Grafana 管理员或数据库管理员访问。

### 10.2 旧 `vm_explorer_favorites` 的可选一次性导入

旧实现曾把指标名写入浏览器。新实现替换这条存储路径，不再读取旧列表作为日常收藏来源，也不继续更新旧 Key。以下流程仅用于用户主动导入已有历史数据；新用户不依赖它。

旧值只包含指标名，且未按用户、组织或数据源隔离。因此不能一登录就把它认定为当前用户的服务器收藏，也不能自动上传。

1. 在管理界面提供“导入旧浏览器收藏”入口；仅在用户点击后读取旧 Key，移除旧 Favorites 日常浏览和保存路径。
2. 用户确认这些条目属于自己并选择当前可用的数据源及待迁移条目；若没有旧数据，显示空状态，不创建任何内容。
3. 为每个指标创建一条表达式等于该指标名的查询，名称同指标名、单位为 none、图形为 timeseries；明确说明这不会恢复旧的标签、聚合、rate 或热图语义。需要自动图表语义的条目可在原浏览页面重新 Favorite。
4. 按每节点最多 20 条分组放入“旧收藏导入”目录；批次前检查总体容量。遇到同名目录时让用户选择已有目录或改名，不能覆盖。
5. 使用稳定的迁移操作 ID 和查询 UUID，按普通条件提交到 Grafana 服务器；失败不删除原始列表，已成功批次显示明确进度。
6. 不把导入进度或迁移提示状态写入浏览器。当前操作进度只存在内存，已提交结果通过服务器的节点与操作回执核对；再次导入时检查服务器已有条目并提示重复风险。迁移成功不自动清空原始 Key，允许用户自行清理；原始数据留存仅是对历史数据的保护，不会成为新功能的数据来源。

新 Favorite 按钮始终向 Grafana 服务器提交新模型，不再修改旧指标列表。第一栏最后一项是从服务器加载的用户菜单；刷新、重新登录、跨设备读取均只使用服务器保存的内容。

### 13.2 端到端验收

- [ ] 从第四栏保存当前最终表达式，过滤和 rate 模式与画面一致。
- [ ] 同一节点追加两条不同查询，刷新并在另一浏览器登录后名称、表达式、单位及顺序一致。
- [ ] 保存后清空全部浏览器站点数据，重新登录后仍能从 Grafana 服务器恢复菜单、查询及配置。
- [ ] 重启使用持久化数据库的 Grafana 实例后，已保存的菜单、节点内容、自增 ID 和版本保持完整。
- [ ] 打开收藏节点，第二栏选择不同查询，第四栏分别得到正确数据源和图形。
- [ ] 无数据源或某个数据源不可用时仍能打开管理界面并操作目录。
- [ ] 文件夹与节点可重命名、排序和跨层级移动，保存后 ID 稳定。
- [ ] 非空文件夹不能删除；删除收藏节点后对应内容 Key 同时消失。
- [ ] 修改过程取消不产生远端目录；编辑已存在节点失败时原内容仍完整。
- [ ] 同一用户两个客户端同时新增节点不会复用 ID；冲突不静默覆盖。
- [ ] 模拟写入成功但响应丢失，重试不会产生重复节点或查询。
- [ ] 正常保存、服务器不可用和权限不足时均不写入任何浏览器持久化介质；只有服务端确认后才显示保存成功。
- [ ] 普通用户 A/B 的菜单互不可见；切换组织或用户无旧缓存闪现。
- [ ] 手写多序列查询不会只显示第一条；截断、多序列上限有提示。
- [ ] 秒、毫秒、字节、0～1 百分比及 0～100 百分比显示正确。
- [ ] 热图保存区分桶单位与值单位；编辑为非直方图后有明确兼容提示。
- [ ] 损坏一个内容值不会清空整棵树；未知版本只读。
- [ ] 旧收藏仅在用户主动导入时读取；需显式选择身份归属与数据源，导入结果保存到服务器，失败不删除原列表。
- [ ] 原 Pod/Node/Metric 浏览、标签过滤、图形类型切换、复制/Explore 链接、列宽与折叠无回归。
- [ ] 浅色/深色主题、窄屏、长名称、深层树与键盘导航可用。

## 14. 风险与发布判断

| 风险 | 后果 | 应对与发布条件 |
| --- | --- | --- |
| SDK 静默本地回退 | 用户误以为跨设备保存成功 | 明确远端 adapter、真实响应确认；不通过则不可发布写入 |
| Grafana 数据库未配置持久化 | 重启或重建容器后丢失已保存数据 | 部署检查与重启恢复测试，不用浏览器存储弥补 |
| 条件提交未验证 | 自增 ID 重复、树或查询被覆盖 | P0 硬性完成并发/原子测试 |
| 直接使用 alpha HTTP 路径 | Grafana 升级后接口变化 | 单点适配、固定测试矩阵、能力失败时保留原有浏览 |
| 保存接口 Key 分离但物理资源整体加载 | 资源膨胀与慢加载 | 整体配额、延迟解码、实测体积/延迟 |
| 回放继续依赖自动 chart-plan | 用户编辑后的查询被改写 | 保存文本直接执行，来源信息仅供显示 |
| 复用单序列图形 | 隐藏查询结果或错误归约 | 独立收藏渲染语义、多序列测试 |
| 数据源/组织切换 | 查询发往错误环境、缓存串用 | 保存 UID、身份作用域隔离、显示当前绑定 |
| 迁移旧数据时猜测上下文 | 错误查询或他人本地收藏被上传 | 用户确认、明确原始指标表达式语义、保留源数据 |
| 故障重试不幂等 | 重复创建、重复追加 | 操作回执、稳定查询 ID、不可判定时停止自动重放 |

发布完成的标准不是“弹窗能保存一次”，而是：**初稿要求的树管理和查询保存全部可用；再次打开可以正确执行；跨设备持久化有实测证据；失败、并发和损坏不会静默丢失数据。**

本计划仍需实施阶段验证的事项已经收敛为：Grafana 条件提交协议及错误码、支持的宿主版本与组织行为、实际存储配额、浏览器 gzip 能力、单位选择组件可用性。其余产品默认行为已在本文确定，不应在编码时再零散猜测。
